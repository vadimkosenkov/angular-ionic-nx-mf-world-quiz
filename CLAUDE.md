Project rules that override defaults:

- **Never fake a feature.** Anything not implemented is labelled as such in the UI and in docs (e.g. the leaderboard shows an honest "not available yet" state until sign-in and the API exist). Docs describe what exists; planned items are marked.
- **Workflow:** implement + tests + docs → run the full verification below → show a summary → **stop and ask before commit, push or PR**. The user merges; never merge or force-push.
- Code, comments, docs, commits and PRs are in English. Every change of substance updates the matching doc in `docs/` (and an ADR when a decision changes).

## Commands

Node `^24.15` (`.nvmrc`), npm. Lockfile is committed; use `npm ci`.

```bash
cp apps/api/.env.example apps/api/.env  # once: API config (Google client id, dev sign-in) — only the API loads it
npm run start:quiz        # shell :4200 + capitals :4201 + flags :4202 + api :3333 (first start ~1 min)
npm run start:shell       # shell only — /quiz/* then shows "Quiz unavailable" (expected)
npm run start:capitals    # a remote standalone (:4201; start:flags → :4202), with in-memory ports
npm run start:site        # public SSR site :4300 (dev server) + api :3333
npx nx run site:serve-ssr # the site's production build on its Node server (:4300, NG_ALLOWED_HOSTS=localhost)
npx nx run shell:ios-sync # builds shell + both remotes into dist/apps/shell/ios-www and runs `cap sync ios` (API_URL=… to point the app elsewhere)
npx nx run shell:ios-open # opens apps/shell/ios in Xcode
npm run start:api         # http://localhost:3333/health — embedded PGlite in .data/pglite unless DATABASE_URL is set
npx nx run api:db-generate  # after editing apps/api/src/db/schema.ts: writes a SQL migration into apps/api/drizzle/
TEST_DATABASE_URL=postgres://localhost:5432/world_quiz npx nx test api  # API tests on a real PostgreSQL (temporary DB per test file)

npm run release           # cut a release: the waiting notes become a dated version (docs/deployment/releasing.md)

npx nx <target> <project>                     # e.g. npx nx test quiz-domain
npx nx affected -t lint typecheck test build  # only what the branch changed
```

Single test file / single test:

- Pure-TS projects (`quiz-domain`, `quiz-countries`, `shared-util`, `api`; plain Vitest): `npx nx test quiz-domain -- src/lib/mastery.spec.ts`, or `-- -t "name"`. Add `--run` in an interactive terminal to avoid watch mode.
- Angular projects (`shell`, `capitals`, `client-*`; `@angular/build:unit-test`): `npx nx test client-ui --include='**/progress-bar.spec.ts'` or `--filter='ProgressBar'`.

Full verification before any commit (this is what CI runs, plus E2E):

```bash
npm run check:control-chars
npx nx format:check                                           # fix with: npx nx format:write
npx nx run-many -t lint typecheck test build --skip-nx-cache
```

Rules that bite:

- `scope:shared` libraries (`type:domain`/`util`/`contracts`) must stay **platform-free**: ESLint bans Angular, Ionic, Capacitor, RxJS, Express, Dexie, Drizzle and Node built-ins there, and their tsconfig has `lib: ["es2022"]`, `types: []` (no DOM, no Node globals). The same domain code is meant to run on the server to re-grade results.
- Remotes (`scope:capitals`, `scope:flags`) may use `scope:client` and `scope:shared`, never the shell or each other.
- The site (`scope:site`) may use only `scope:shared` (contracts, quiz domain, design tokens): no Ionic, no `client/*` — it has its own typed texts (`apps/site/src/app/i18n`).
- Imports use tsconfig path aliases `@world-quiz/<group>/<lib>` (`tsconfig.base.json`); no npm workspaces. Test-only entry points: `@world-quiz/quiz/domain/testing` (fixture dataset), `@world-quiz/client/quiz-feature/testing` (`provideQuizTesting()`) and `@world-quiz/client/progress/testing` (`finishedSession()`, `historyEntry()`, test users); never import them from production code.
- `@typescript-eslint/consistent-type-imports` is on: type-only imports use `import type` / `type X`.

### Domain model (`libs/quiz/domain`)

Everything is deterministic and immutable so the server can later **replay** a session to validate it: seeded PRNG (`random.ts`), `createQuizEngine(dataset)` returning new session objects from `start` / `submitAnswer` / `stop` / `expire` / `summarize` / `replay`. Time always comes from an injected `Clock`. Questions are regenerated from `seed` rather than stored. The client never sends score, rank or mastery as facts — only answers. Rules are documented in `docs/domain/*.md`.

### Microfrontends (Native Federation)

Read `docs/architecture/microfrontends.md` before touching federation. Key points:

- `apps/*/src/main.ts` only calls `initFederation(...)`, then imports `bootstrap.ts`. The shell reads `apps/shell/public/federation.manifest.json` (`capitals` → :4201, `flags` → :4202).
- The shell mounts `/quiz/capitals` and `/quiz/flags` via `loadChildren: () => loadQuizRemoteRoutes(name)` (`apps/shell/src/app/quiz/remote-routes.ts`), which falls back to a "Quiz unavailable" page and reports to `ErrorHandler` if loading fails.
- Both remotes expose `quizRemoteRoutes(category)` from `client/quiz-feature`: the shared `QuizPage` with the category in route `data`. Practice Mistakes is `?mode=practice` (the page reads the category's mistakes from `QUIZ_PROGRESS_READER` once per round, filtered by `scope`, up to `PRACTICE_ROUND_SIZE` = 20, and plays a `fixed` quiz with `countryCodes`). Nothing in the URL says anything about a board: the page hands the finished session and its summary to `QUIZ_RESULT_SINK.submit()` and shows `outcome.ranked` when there is one (a promise of the server's `RankedOutcome`, `null` if unsent) — the host decides whether the run could rank at all, with the same domain function the API uses. A remote contains no screens of its own — its value is its separate build, dev server, `remoteEntry.json` and URL. Adding a quiz type = new app + one-line `remote.routes.ts` + manifest entry + host route + E2E server.
- The contract lives in `libs/client/quiz-ports`: `QUIZ_RESULT_SINK`, `QUIZ_PROGRESS_READER`, `COUNTRY_DATASET`, `CLOCK`, and `QuizRemoteRoutesModule` (the compile-time type of the exposed module). The shell provides implementations **on the route** with `provideQuizPorts()`; the remote never reaches shell stores. Quiz options travel as query params bound with `withComponentInputBinding()`.
- Only **finished** sessions go to the sink (all questions answered, Timed expired, Endless "Finish"). Leaving via the exit button abandons the session and records nothing.
- Workspace libraries are shared through the tsconfig path mappings, so tokens and the dataset exist once at runtime. A library missing from `shared` in `remoteEntry.json` produces duplicate `InjectionToken`s and `NullInjectorError` inside the remote.
- A remote's `app.config.ts` / `app.routes.ts` / `App` exist only for standalone dev, using `provideInMemoryQuizPorts()`.

### Backend (`apps/api`)

Read `docs/architecture/backend.md` and ADR-005 first. Key points:

- Layers: `sessions.routes.ts` (parse with the `shared/contracts` Zod schema, map outcomes to status codes) → `session-service.ts` (plausibility, `engine.replay`, idempotency) → `session-repository.ts` (SQL only) → `db/database.ts`. `createApp()` takes its dependencies; `main.ts` is the only composition root.
- **The server grades.** Requests carry config, seed, timestamps and answers only (strict schema: `score` etc. are rejected). The service replays the session with `quiz-domain` and stores the server's results; a session that cannot be replayed is rejected (422), never corrected.
- Idempotency: client-generated UUID `id` (normalised to lower case by `uuidSchema`) + SHA-256 of the canonical, contract-parsed request (`request-hash.ts`). Never give a new request field a `.default()`: older clients' retries would hash differently and get 409. Same body → 200 with the stored result; different body → 409; races resolved by the primary key + `ON CONFLICT DO NOTHING`.
- One body from before Phase 25 is still accepted: a device that finished a leaderboard **challenge** offline holds that request in its outbox. `parsePostedSession` (`shared/contracts`) tries today's contract first, then the legacy shape, and translates it into a quick round over the World set (same seed, same questions, same grading); the challenge id is dropped and the run is **never ranked** (195 questions is not a quick round's length, and `SubmitOptions.legacy` says so as well). Refusing it would mark a real game as `rejected` and drop its answers from the player's progress.
- Every error is RFC 9457 `application/problem+json` (`http/problem.ts`); 500s are logged, never leak details.
- Two drivers behind one `Database` type: `pg` pool (`DATABASE_URL`) or PGlite (tests: in memory with the real migrations via `createTestDatabase()`; dev: `.data/pglite`). Production requires `DATABASE_URL`. Migrations run at start-up.
- **Auth** (ADR-010, `src/auth/`): the client sends a provider ID token; `identity-verifier.ts` checks it against the provider's JWKS (`jose`), `user-repository.ts` maps `(provider, sub)` to a user. The API issues a 15-min HS256 access token (`Authorization: Bearer`) and an opaque refresh token (SHA-256 stored) that **rotates with reuse detection** (reused → whole family revoked). Refresh token delivery: httpOnly `SameSite=Strict` cookie `wq_refresh` scoped to `/v1/auth` (web) or the response body (native, `refreshTokenIn: 'body'`). `requireAuth` guards `/v1/me` and `/v1/sessions`; `currentUserId(response)` reads the user.
- `POST /v1/auth/dev` exists only with `AUTH_DEV_LOGIN=true` and is refused in production (config). Tests never need real Google/Apple: `testing/fake-identity-provider.ts` signs ID tokens with its own RSA key served as a local JWKS; `testing/test-api.ts` wires the whole app (`signIn()` returns a bearer header).
- Deleting a user cascades to identities, refresh tokens and sessions. A still-valid access token of a deleted user gets 401 where it matters (`owner-missing` on session insert).
- **History** (`GET /v1/sessions?after=&limit=`): the player's sessions with graded answers, keyset-paged on `(recorded_at, id)` with an opaque base64url cursor (`history-cursor.ts`) that a client keeps for later pulls. Sessions appear only after `HISTORY_SETTLE_MS` (5 s), so an insert still committing cannot land behind a cursor. Row comparison in SQL: `(recorded_at, id) > (…)`.
- **Leaderboards** (`src/leaderboard/`, docs/domain/leaderboard.md, ADR-014): there is nothing to start — every session is graded, and `ranked-run-rules.ts` decides whether the replayed run belongs on a board (the domain's `evaluateRankedRun`, plus a plausibility floor of `MIN_RANKED_ANSWER_MS` = 250 ms per answered question; without a server-issued seed nothing else about a time can be proved, and offline results must still rank, so there is no lateness check). A ranked run is one row in `leaderboard_runs` (keyed by the session, written in the session's transaction) carrying the board, the score, the run's time and one ascending `rank_key` from the domain's `rankingKey()` — the time, or the negated count — so all 56 boards share one `ORDER BY` and one index. Rankings are queries: `selectDistinctOn([board, userId])` (best per player) + `row_number()` in `compareLeaderboardEntries` order; a test compares them with `rankLeaderboard`. Boards are public and show **nicknames** only (`users.nickname`, default `defaultNickname(id)` = "Player NNNN"; never the provider's name); `/v1/me/records` carries the player's own nickname, so the app's pinned row needs no account data of its own and is matched to the public board by rank, which is unique there; a board of friends numbers its places over fewer people, so the app finds the player's row by `recordedAt` plus nickname and marks at most one (two runs can share a millisecond — `compareLeaderboardEntries` breaks that tie by session).
- **Friends** (`src/friends/`, ADR-015): a player is found only by the permanent 8-character invite code `GET /v1/me` hands back (Crockford base32; `normaliseInviteCode` in the contracts reads what was typed — case, spaces, dashes, `I`/`L` as `1`, `O` as `0`). There is no search and no directory. A friendship is **mutual** and is one row in `friendships` keyed by the pair, in the direction it was asked: asking somebody who has already asked you accepts their row instead of inserting a second one, and declining a request and unfriending are the same `DELETE /v1/friends/:id`. The primary key only covers one direction, so the pair also carries a unique index over its two ids sorted (`friendships_pair_idx`): without it two people asking each other at the same moment write two different keys and both get through, and each ends up in the other's incoming **and** outgoing list. `request()` hands back the row's own `since` (what the lists will show), never the other player's `createdAt`. A player who is not a friend gets **404, never 403** (whether an id exists is private), and every answer is `no-store`. A friend's page carries their records and their achievements, which are computed on request from their stored answers with the domain the device uses (`rebuildProgress` + `evaluateAchievements`) — mastery is never stored. `GET /v1/friends/leaderboards/:board` is the public board's own query with `among` = the player and their friends, so all 56 boards still share one `ORDER BY` and one index.
- `/v1/auth` is rate-limited per client address (`AUTH_RATE_LIMIT`, default 30 per 15 min); `api:serve-e2e` raises it because every E2E test signs in.
- Not yet: native Apple sign-in, Keychain storage and Apple token revocation (Phase 13).

### Public site (`apps/site`)

Read `docs/architecture/site.md` and ADR-003. Key points:

- Every page is under `/en` or `/ru` (`canMatch`); `server.ts` redirects `/` by `Accept-Language`. `app.routes.server.ts`: home and legal pages `RenderMode.Prerender` (`getPrerenderParams` per language), everything else `RenderMode.Server`.
- The leaderboard page uses `httpResource` with `leaderboardSchema`; the response travels to the browser in the HTML (transfer cache). It sets `RESPONSE_INIT`: `public, max-age=30`, or `503` + `no-store` when the API is down; unknown pages are real `404`s.
- `SiteLayout` sets the language (`SiteI18n`), `<html lang>`, canonical and `hreflang` links. Texts: `i18n/en.ts` + `ru.ts: SiteText`.
- Server configuration from the environment in `app.config.server.ts` (`siteConfigFromEnvironment`: `API_URL`, `SITE_URL`, `APP_URL`, `SITE_OPERATOR_NAME/EMAIL`); without an operator the legal pages show a **draft** notice (nothing personal in the repo). The legal texts describe the service as built — change them with the code. The values travel to the browser in `TransferState` (`SITE_CONFIG_STATE`), or links would point at localhost after hydration; because home and the legal pages are prerendered, the site's image is built per environment (ADR-012).
- SSR in the shell was spiked and rejected (ADR-003): IndexedDB, Capacitor Preferences, sign-in and Ionic all break on the server, and it would render only `/welcome`.

### Frontend conventions

- Stores are signal-based `@Injectable` classes (`ProgressStore` and `SyncService` in `client/progress`, `SettingsStore`, `AuthStore`, per-page `QuizSessionStore`).
- **Progress and sync** (ADR-006, `client/progress`): the device keeps finished sessions (`LocalSession`: `pending` / `synced` / `rejected`) in IndexedDB via Dexie behind the `LocalStore` port; progress is **rebuilt** from their events (`rebuildProgress`, canonical order), never stored. The shell's sink calls `ProgressStore.recordSession()` then `SyncService.sync()`. The sync sends the outbox oldest first (`POST /v1/sessions`, idempotent by id), then pulls `GET /v1/sessions` pages from the stored cursor. 400/409/422 → `rejected` (not counted, reported, shown in Settings); offline/5xx/429 → retry after 5 s, 30 s, 2 min, 10 min. Triggers: signed in, finished quiz, `online`, back to foreground. A run that succeeds **after** failing exposes `recovered` (how many waiting results went through); the shell's `provideSyncNotices()` turns that into a message, and only that one — an ordinary sync says nothing. The device's data has one `owner`: `claim(user)` deletes another account's data first; sign-out and account deletion call `forget()`.
- **Leaderboard** (`apps/shell/src/app/leaderboard`): `httpResource` on the public board and `/v1/me/records`, parsed with the contract schemas. A board is the four settings a quiz is played with, so it is chosen with the very controls the quiz setup asks those questions with — the shared `.wq-option` tiles for category and difficulty, `wq-region-options` for the region, a row per ranked mode saying what that board asks of a player — over `leaderboardBoardFor()`. Nothing is **started** here (any game in a ranked mode competes; which modes are ranked is said by the "i" beside Game mode on the setup instead): the page's button **shows** the board, and the ranking opens over it in a `wq-dialog` whose own title is just "Leaderboard" while a centred trophy header names the board as two lines (category · region, difficulty · mode — as one line it wrapped after the third setting on a phone); pressing it again reloads, and nothing is fetched until asked for, because four choices and a table do not fit on a phone together. The picker opens where the player left it (`linkedSignal`s over `LastSetupStore.board()`, remembered on "Show" — a separate fact from the quiz setup's own memory). The player's own row is highlighted in place and pinned under the list when their place is below the page shown. Records and an open board reload on `ionViewWillEnter` **and** when `SyncService.lastSyncedAt` changes. `SyncService.resultOf(id)` gives the API's answer to a session sent now (the place it earned). Times are shown with `formatRunTime` (`m:ss.t`, `client/quiz-feature`). The nickname is edited in Settings → Account (`AuthStore.setNickname`, validated with `nicknameSchema`).
- **A record is the loud case on the results** (`client/quiz-feature/quiz-results`, design-system.md): a personal record turns the board card into the brand gradient — trophy, "New personal record!", the board, and the place and score as two labelled figures, with one sheen that does not move under `prefers-reduced-motion` — and the hero's single share hands over the **record's** picture (`recordShareCard`, in `client/ui` so both screens build it). An ordinary place stays a plain card with a gold/silver/bronze medal (`--wq-color-medal-*`) for the first three; being checked and waiting offline stay quiet. The shared picture says the same things in its own drawing (`recordShareCard`): a white card under the primary band, the trophy over the claim, the board, and the medal beside the figure.
- **Sign-in is required before playing** (ADR-011): `/welcome` is the only public route; `signedInGuard` waits for `AuthStore.whenRestored()`, claims the device for a signed-in player, and lets an `unverified` (offline) player in only if they own the device's data. `provideSignInFlow()` returns to `/welcome` (new navigation root) when a sign-in ends.
- Sign-in on the web (`client/auth`, Settings → Account): Google's button via Google Identity Services (not the Capacitor social-login plugin — its web code stores tokens in `localStorage`); the access token only in `AuthStore` memory, the refresh token only in the httpOnly cookie; `provideAuth()` restores at start-up; `authInterceptor` adds `Bearer` to `API_URL` requests only and renews **once, shared** on 401, and across tabs under a Web Lock (parallel refreshes would trip reuse detection). Only a 401 from `/v1/auth/refresh` signs out; offline, 5xx, 429 or a contract error keep the player signed in, or `unverified` at start-up. Google's button gets a fresh nonce after every attempt. API URL, Google client id and the app's own public address (`appUrl`, the link in a shared result) are **read at start-up** from `config.json`, not compiled in (`apps/shell/src/app/runtime-config.ts`, ADR-012); `appConfig(runtime)` takes them as an argument and `bootstrap.ts` loads them first.
- **Messages** (`client/ui`, design-system.md): `Toasts` holds one transient message and `wq-toast-host`, rendered once in `App` outside the router outlet, shows it at the bottom over the chrome; the shell's `AccountNotices` picks the text, because `client/ui` has no translations. A toast reports the outcome of an action the player just took (name saved, sign-in failed, signed out, account deleted, a retry that failed again, results that finally reached the account after waiting offline); a standing fact about a screen — a refused result, an empty board, offline, the nickname rules — stays on that screen. A failure is `role="alert"` and lasts longer, a confirmation is `role="status"`, and every message is rendered as a **new element** (`@for` over a list of at most one) or a screen reader may not announce it.
- **Sharing** (`SHARE_TARGET` in `client/ui/share.ts`, frontend.md, design-system.md): one way out of the app — `navigator.share` where there is a sheet, the clipboard where there is not, answering `shared`/`copied`/`cancelled`/`failed`. It defaults to the browser, so no screen needs a provider. The results screen has **one** quiet round icon button (the hero's corner) and "My records" one per row, each with an `aria-label` (a record's names its board); the results one hands over the record's picture when the run set one, and the run's otherwise. A message is built only where a file cannot travel: translated lines joined by `shareLines()`, opening with the same claim the picture leads with, plus the address of this deployment, which arrives as `APP_URL` from the host (`client/quiz-ports`) because a remote cannot know it and the iPhone app's origin is the bundle. Only `copied` and `failed` are reported in a toast: an opened sheet is its own confirmation, and a closed one was the player's answer.
- **What is shared is a picture, and it travels alone** (`client/ui/share/share-card.ts`, `share-claim.ts`, frontend.md, design-system.md): a 1080px square **drawn** on a `<canvas>`, handed to the sheet with **no text and no url** beside it — an app that receives both may post them as two things, and the text then repeats the card. So the card explains itself, in reading order: a **claim in the player's voice** ("New personal record!", chosen by `shareClaim` — a record beats a place, a place beats a flawless run, and `plain` claims nothing it cannot back up), the figure that backs it, what was played, where the run landed — a place in the first three as a filled **gold** disc (`--wq-color-hint`, the same for all three places — silver and bronze are a grey and a brown disc, and the number says which place it was) with the number in white, the largest thing under the claim — and one line daring the reader to beat it, in the app's own colour. A board the player is alone on says "First result on this board" rather than "#1 of 1". Both pictures are one object — a white card under a band in `--wq-color-primary` carrying the name — and a **record** is told apart by the trophy over its claim (Ionicons' `trophy` path, since a canvas has no icon font) and by the row under it, where the medal and the figure the record was set with stand side by side, divided by a hairline, the figure labelled underneath ("Time", "Correct") and bare ("21", not "21 correct") because beside a medal there is only room for a number; a run's card keeps its big headline figure and ends with accuracy and time, whose labels sit above them as on screen. Screenshotting the DOM is not an option (the results card is glass over a blurred backdrop, and Ionic lives in shadow roots), and drawing also makes the picture identical everywhere. Colours come from the `--wq-*` tokens on `<html>`, so the card follows the player's theme, and the app's system font stack means nothing has to be embedded. The layout is a pure function (`shareCardPlan`, which centres its blocks between the band and the invitation) tested without a canvas; `drawShareCard` executes it and each text carries the width `fillText` condenses it into. The words are built outside the components too (`runShareCard` in `client/quiz-feature`, `recordShareCard` in `client/ui` — the results screen and "My records" share one record picture). The picture is offered **only** where `canShare({ files })` says yes; where it is not, the text is the whole message and carries the address.
- **A sound for starting something** (`client/feedback`): `FeedbackEvent` has `start` beside `correct`/`incorrect`/`finished`/`celebrate` — a rising fourth below the answer tones, played on the **press** (quiz setup's Start, Play again), not when the quiz appears; a press that only opens a screen stays silent.
- **The account card is a list of rows** (`apps/shell/src/app/settings/account-section.*`, design-system.md): identity, nickname and the two commands are rows of one card divided by hairlines, iOS-style. The card has no padding and every row (`.row`, `.account-action`) carries its own, which is what lets a hairline run its full width; a row is **56 px** with 16 px of side padding, the same as the `ion-item` rows of the other Settings cards, or this card reads as a different kind of thing. A row that says something is an icon, a 16 px/600 first line and a `.note` second line at `--wq-font-size-subtitle` (14 px) — the same two lines a language row has, because rows that look alike must not be a pixel apart; the identity row leads with the mark of the provider signed in through. A `wq-info-button` on such a line takes `--wq-info-size: 24px` **on the host** (the button it scales is inside that component, out of reach of a rule written outside), or the row grows past 56 px. What the card asks is a `wq-dialog`, not a panel inside the card; `.panel` is left for the retry button of an account that could not be checked, and `.account > :first-child` drops the line above whichever branch of the `@switch` came first. The card says only what is news: there is **no** permanent "all your results are saved" row — a sync row appears only while something is saving or waiting (a refused result keeps its own), so silence means saved, and the E2E suite asserts `sync-status` does not exist.
- **A dialog in the middle of the screen** (`wq-dialog` in `client/ui`, design-system.md): a backdrop and a centred card, used for every question Settings asks (a new name, signing out, deleting the account). Centred rather than pinned to the foot, because on iOS the keyboard is invisible to CSS and takes the bottom of the screen; when it opens the card is nudged up by exactly what the keyboard would cover and no more (re-centring it in the room left threw it halfway up the screen), measured from `visualViewport` with iOS's own lift of the document undone. After the first render the host element is **moved to `document.body`**: `ion-router-outlet` is its own stacking context below the floating tab bar, so a dialog left in the page leaves the tabs lit and clickable behind its backdrop — and the node is removed by hand on destroy. `closeLabel` is what draws the round close button, so a dialog with a cancel of its own does not offer the same way out twice; Escape and the backdrop always work, the card takes the focus, Tab stays inside, and the focus returns to whatever opened it. `tone="danger"` makes it an `alertdialog` and colours the **title only**. Built by hand rather than with `ion-modal`, which does not upgrade in jsdom.
- **Held, not pressed** (`wq-hold-button` in `client/ui`): deleting the account fills over 1.6 s and acts only when the press has lasted — a second confirmation dialog is a question people learn to click through, while a mis-touch is short by definition. Letting go runs the fill backwards; holding Space or Enter is the same gesture. The line under it is the button's `aria-describedby` and takes the colour of the action (`--wq-hold-hint-color`); inside the button it made a block half a screen tall on a phone. A development build (`devSignIn`) shows a second button beside it that deletes nothing, so the hold can be rehearsed.
- **Which version is running** (`app-info.ts`, Settings → About, deploying.md): `<meta name="wq-version">` and `<meta name="wq-build">`, both written into the finished bundle by `tools/scripts/stamp-build.mjs`. The version is `major.minor` from `package.json` plus the commit count as the patch, so every deploy publishes a new number with nothing committed — a bump at deploy time would make the build stamp say `-dirty`. The two leading numbers are raised by hand with `npm run version:minor` / `version:major`, which deliberately write **no tag** (a `v*` tag starts the production pipeline). An unstamped build says "development" rather than inventing a number.
- **What changed in this release** (`apps/shell/src/app/release-notes/`, `NotificationsStore`, frontend.md, deployment/releasing.md): the notes ship **in the bundle** as JSON (`releases.json`: an `unreleased` block plus dated entries with `en`/`ru` lines), because they describe the code they are built with and because `npm run release` rewrites the file — a script editing a TypeScript literal would be a regex away from breaking the app; a test over the real file checks what types cannot (both languages the same length, each version once). The bell in the far corner of Home's header (`.wq-header-action`, projected into `wq-page-header`) is a **list** of what the app has to say — today one unread release, friends' challenges next — and says "nothing new" rather than disappearing. The mark is a dot on the bell and on Settings → What's new; **opening the page** clears both, not pressing the bell. The release the player has read lives in `KEY_VALUE_STORAGE` beside the tours: it belongs to the device, not the account. A device with nothing stored is level with the build it starts on, so a new player is never invited to read what they have not missed — which is why release 0.4, the first with this screen, goes unannounced. A deploy is a release: `npm run release` moves the minor and dates the entry, `deploy:web` refuses while lines are waiting, and `deploy:web:no-note` is the deploy that is not news. The `/release` skill (`.claude/skills/release/`) writes the missing lines from the commits.
- **Hints** (`wq-tour-step` in `client/ui`, `TipsStore` in `apps/shell/src/app/core`, design-system.md): a screen whose point is easy to miss gets a guided tour, one step per choice; the quiz setup has the first (type → region → difficulty → mode). The step's section is left alone and scrolled to the top of the page, `wq-tour-spotlight` dims the rest of the screen through a `clip-path: path()` with a rounded window where that section is (below the floating header, so the way out stays lit), the other sections are `inert`, and the tour's card stands next to that section — under it, over it, or at the foot of the screen for a section too tall for either — in place of the page's action bar, so the quiz cannot start until the tour is over. Both are placed from one measurement of the section (`trackRect`, every frame: a scroll event never leaves the shadow root of the element Ionic scrolls), and the page keeps a screen's worth of room at its foot while the tour runs, or the last section could not be scrolled to the top. Nothing travels between steps: `whenArrived` reports the section only once it has stood still for a frame, so the card fades out where it stood, takes the next step's words out of sight and fades in beside the new section (a layer placed from a rectangle lags the browser's scroll by a frame and shivers). The card is two rows — words and the way on, then the dots — is exactly as wide as the lit window (both get their sides from the same rectangle), and both leave with the page (`wqFadesWithPage`), or the tour stays lit over the screen the player has already reached. It runs once: what has been seen and whether tours are wanted at all live in `KEY_VALUE_STORAGE` with the settings — they belong to the device, not to the account, so signing out does not bring a tour back. `provideTips()` loads them before the first render. Settings → Screen tours is one switch for `TipsStore.on()` ("a tour is still going to appear"): it goes off by itself once the last one is walked, turning it on forgets what was seen, and turning it off refuses later tours too — hence the separate `enabled` flag. `.wq-row` in `client/ui/src/styles/_base.scss` is the shared "what it is + a pill action" row (Home's Practice mistakes), and `.wq-card-rows` beside it is the inset a `.wq-card` holding rows takes — the card itself has no padding, because what goes inside decides.
- **Friends** (`apps/shell/src/app/friends`, ADR-015, frontend.md, design-system.md): `FriendsStore` is the one place the three lists live — `httpResource` on `GET /v1/friends`, which asks for nothing while nobody is signed in — and every mutation **reloads** them rather than patching (accepting a request empties one list and fills another, and the server knows what the result was). Home's third `.offer` card and the bell read the same signals, so a waiting request is news on the first screen; the card carries the bell's own mark, and `ionViewWillEnter` asks again because requests arrive while the app is open. The invite is a `wq-dialog` behind the `+` in the header (the screen itself is the list of people): the code as a QR (`wq-qr-code` in `client/ui` — one SVG path, white background, **not** themed, because a scanner needs dark-on-light), as two groups of four, a share, and the field for somebody else's code. What the app can judge itself it judges before sending — `inviteCodeSchema`/`normaliseInviteCode` from the contracts, and the player's **own** code is refused in the app — and says so beside the field, not in a toast. `/invite/:code` is the only route besides `/welcome` outside the sign-in guard: it writes the code into `KEY_VALUE_STORAGE` (the device's note, not the account's), waits for `whenRestored()` and sends the player on, while `FriendsStore` sends the request from an `effect` on `signedIn()` and **forgets the code whatever came of it**. It reads the route input inside an effect, not in the constructor — a required input read before the router sets it throws. A friend's page is `GET /v1/friends/:id` (records with a medal for the first three, achievements, the furthest first); a page that is not yours to see is the API's 404 and says the same; any other failure is the connection and gets the list's offline card with a retry, never "you are not friends any more". Ending a friendship is asked for there, in a `tone="danger"` dialog. The ranking's audience segment swaps the public board for `GET /v1/friends/leaderboards/:board` and **drops the pinned row**: the rank a record carries is the public one.
- **The countries reference** (`apps/shell/src/app/countries`, frontend.md): `/countries` is pushed over the tabs from Home's "Learn" row — every country of the chosen region (the same `QuizScope` as the quiz setup) with its capital and its flag, sorted with an `Intl.Collator` of the display language, because the dataset's own order is by region. `country-rows.ts` builds the rows outside the component, so they are tested without rendering. The capital and the flag are marked **separately** when `isMastered` says so, each with a tick on a light green disc placed over it (absolute, so a lit row moves nothing; plus `wq-visually-hidden` words, because colour alone says nothing to a screen reader): mastery is kept per category (`capitals:fr` and `flags:fr` are separate states), so a single mark for the country would claim knowledge the player may not have. Nothing here needs the API — dataset plus the device's own progress.
- **One way into the quiz** (`apps/shell/src/app/core/last-setup.store.ts`, frontend.md): Home has a single Play card — the same big card the two category cards used (`.offer`, design-system.md), now one, beside a Learn card of the same shape — and it says what pressing it will start — the four words of the setup the player last played. `LastSetupStore` keeps that setup (category, region, difficulty, training mode) — and, under a key of its own, the board the leaderboard last showed — in `KEY_VALUE_STORAGE` beside the tours: it is the device's convenience, not the account's, and `provideLastSetup()` loads it before the first render. The setup screen seeds all four choices with `linkedSignal`s over the store, so the player moves them freely and the screen starts from the remembered setup whenever it is opened afresh, while a query parameter still wins (`?category=&mode=practice` from Home's Practise rows). Only `start()` remembers, and **Practice Mistakes is never remembered** — it is an action, not a preference, and coming back to it would mean a disabled Start button. The two modes that play against everyone else are listed first and carry a small "Ranked" pill beside the name (sub-headings over two groups were tried first: they split one short list in two and still put the fact somewhere other than the row it is true of). **Start quiz is in the page**, under the last choice, not in a floating `.wq-action-bar` — a button pinned to the foot is on screen before the choices it uses are — and it is hidden while the tour runs; the leaderboard's "Show the board" is the same button in the same place (design-system.md, "Actions live at the bottom"). The category and the difficulty are chosen there as square tiles (`.wq-option.tile`: what the quiz asks for plus mastery, how an answer is given), not as segments — the hint that used to sit under the control is inside the tile it belongs to — and the region grid is `wq-region-options` (`client/ui`), shared with the countries reference: each option carries a hand-drawn globe used as a CSS **mask** (`libs/client/ui/src/assets/regions/*.png`), so one grey+alpha file serves both themes and the selected state. The options come from `regionOptions()` (`apps/shell/src/app/core/region-options.ts`) — `client/ui` holds no translations, so the names arrive translated.
- **A note belongs to its setting** (`wq-info-button` in `client/ui`, design-system.md): a setting's explanation sits behind an "i" right after its name (in the primary colour, so it reads as something to press; the row hands back Ionic's growing label with `.setting ion-label`) and opens in an `ion-popover` anchored to the press, not as a paragraph under the card — stacked notes read as one block and say nothing about which control they are for. A disabled control still explains itself without being asked: the vibration toggle keeps its reason in a `wq-visually-hidden` paragraph it points at with `aria-describedby`. Its name is dimmed with `opacity: 0.5` on the label alone (`disabled` on the `ion-item` would also take the `i` button's taps) and carries `aria-disabled`, which is both true and what makes axe apply the contrast exemption an inactive control has.
- **Sound and haptics** (`client/feedback`, design-system.md): `Feedback.play(event)` plays a Web Audio tone and, in the app, a taptic tap; `TONES` and `HAPTICS` default to doing nothing, so tests and server rendering need no setup, and `provideFeedback({ native })` installs the real ones. The quiz plays `correct`/`incorrect` when the verdict appears and `finished`/`celebrate` on the results. Both channels obey `SettingsStore.sound()` / `.haptics()`, and every failure is swallowed.
- `provideAppSettings()` loads settings and the translation file in an app initializer, so theme and language apply before first render. Dark mode is Ionic's class-based palette (`ion-palette-dark` on `<html>`).
- Translations are TypeScript objects in `libs/client/i18n/src/lib/translations/{en,ru}.ts`; `ru` must match the `TranslationShape` of `en` (compile-time + unit test). Plurals use `wqPlural` (`Intl.PluralRules`). Country names never go into translations — they come from the dataset.
- Ionic runs in `mode: 'ios'` on every platform. Ionic's `ionChange` events are not Angular outputs under strict templates: handlers take `Event`, cast to e.g. `SegmentCustomEvent`, and validate the value with the domain guards (`isDifficulty`, `isQuizScope`, …).
- Design system rules (`docs/architecture/design-system.md`): colours only via `--wq-*` tokens (light + dark defined), one glass material (`glass-chrome($top-highlight)`, a mixin in `client/ui/src/styles/_materials.scss`, which carries the opaque fallback and the reduced-transparency rule itself — never override its background after including it) for the tab bar and the floating page header (`wq-page-header` — the shell has no `ion-header`), a page's next action in the bottom `.wq-action-bar` with `ion-button.wq-glass-button` (solid fill), except the quiz verdict, which is itself the control that continues, control text `--wq-font-size-control`, captions `--wq-font-size-caption`. Icons must be registered explicitly (`apps/shell/src/app/icons.ts`, `registerQuizIcons()`).

### Installable web app (`docs/architecture/pwa.md`)

- `apps/shell/public/`: `manifest.webmanifest`, `icon.svg` and the rendered `icons/` (regenerate with `node tools/scripts/render-icons.mjs`), and a hand-written `service-worker.js`. Angular's service worker is not used: the app is three deployments on three origins, and its builder only knows one of them.
- Cache rules: `/v1/*` never; pages network-first; the files a deployment rewrites in place network-first (`MUTABLE`: `config.json`, `federation.manifest.json`, `remoteEntry.json`, `manifest.webmanifest` — cache-first would freeze an installed app on the previous deployment); everything else cache-first (hashed filenames). Bump `CACHE` in the worker to drop old entries. The rules are tested by really running the worker against a fake `caches`/`fetch` (`apps/shell/src/app/service-worker-rules.spec.ts`; reading the file is why the shell's `tsconfig.spec.json` has Node's types).
- `registerServiceWorker()` skips `localhost` (a worker serving yesterday's chunk during development wastes an afternoon) and registers immediately when the page has already loaded — the app often starts after `load` because its modules come through the federation's import map.

### Accessibility and security (`docs/architecture/accessibility.md`, `security.md`)

- Every screen is checked with **axe** (WCAG 2.2 A/AA) in `accessibility.cy.ts`, including the public site; violations print the offending element. Waive a rule in the spec with a reason, never by shrinking the rule set.
- Ionic's `ion-list` gives its element `role="list"`, so it may only wrap list items — a radio group or a form inside one is a violation. A page with nothing focusable needs a focusable scroll area (`tabindex="0"` on the list).
- The API sends `nosniff`, `frame-ancestors 'none'`, `no-referrer`, a closed `Permissions-Policy` and `Cache-Control: no-store` (`http/security-headers.ts`). The site sends a real CSP with a **per-response nonce**, because Angular's hydration inlines two scripts into every page (`apps/site/src/server.ts`).

### Testing

- API tests that move the manual clock past 15 minutes must sign in again (access tokens expire); `leaderboard.api.spec.ts` plays real sessions with `playSession` and sets the clock to when each result "arrives".
- API tests use supertest against `createApp()` with an in-memory PGlite from `apps/api/src/testing/test-database.ts` (or a temporary PostgreSQL database per file when `TEST_DATABASE_URL` is set — PGlite runs one query at a time, so concurrency is only real on PostgreSQL), and build requests by really playing a session (`testing/play-session.ts`) instead of hand-writing answers.
- Vitest everywhere; Angular projects run through `@angular/build:unit-test` with `buildTarget: shell:esbuild:development` (AnalogJS does not install with Angular 22) and `setupFiles: tools/testing/jsdom-setup.ts` (jsdom lacks `matchMedia` and `scrollTo`).
- Component tests use Testing Library and dispatch Ionic events as DOM events (`ionChange`, `ionInput`); Ionic web components do not upgrade in jsdom, so behaviour that needs them (e.g. input focus) is covered in Cypress.
- Shell pages render with `provideShellTesting()` (in-memory storage, manual clock, chosen locale).
- E2E selectors use `data-testid` or roles. Every journey starts with `cy.signIn()` (dev sign-in via `cy.request`, a new player per call, so tests never share an account or the device's data); `API` is exported from `support/commands.ts`.
- The E2E suite runs **silently**: `support/e2e.ts` replaces `AudioContext` before each page loads, because the specs play real quizzes and every answer made a sound. Do not silence it through the app's own setting — that setting is persisted, and the specs about what survives a reload would then test the seed.
- Accessibility checks: `expectAccessible()` from `apps/shell-e2e/src/support/accessibility.ts` (axe). The site's pages are visited directly on `:4300`; `cy.visit` moves the whole test to that origin, so no `cy.origin` is needed.
- E2E quiz helpers live in `apps/shell-e2e/src/support/quiz.ts`: `answerChoice()`, `askedCountryKey()` (the dataset through the `country` task in `cypress.config.ts` — the spec bundler does not resolve `@world-quiz/*` aliases), and `controlQuizTime` + `advanceQuizTime()` to end a Time attack by shifting `performance.now()` (never `cy.clock()`: it freezes `setTimeout` and the zoneless change detection). `phone-layout.cy.ts` runs at `iphone-x` size; other specs use the default viewport.
- `client/progress` tests use an in-memory `LocalStore`; the Dexie implementation is tested on `fake-indexeddb` (`import 'fake-indexeddb/auto'`, a new database name per test). `SyncService` tests inject `SYNC_SCHEDULER` to run retries by hand.

### iOS (`docs/deployment/ios.md`, ADR-013)

- The app is `apps/shell` in Capacitor 8 (`apps/shell/capacitor.config.ts`, Xcode project in `apps/shell/ios`, committed; what `cap sync` regenerates is git-ignored). Dependencies use Swift Package Manager, not CocoaPods.
- **The remotes ship inside the bundle**: `tools/scripts/build-ios-bundle.mjs` copies the shell's and both remotes' production builds into `dist/apps/shell/ios-www` and writes a manifest with relative paths plus `config.json`. Application code is unchanged — only the manifest differs from the web.
- **Sign-in in the app is native** (Google refuses its sign-in page inside a web view): `NATIVE_SIGN_IN` (`client/auth`, implemented with `@capgo/capacitor-social-login`) returns an ID token for the same `POST /v1/auth/google`, and `REFRESH_TOKEN_STORE` keeps the rotated refresh token in the **Keychain** (`@aparajita/capacitor-secure-storage`) because a web view has no cookie; the API already supported `refreshTokenIn: 'body'`. Both are provided only on the native platform (`apps/shell/src/app/app.config.ts`, `core/platform.ts`), and `AuthStore.restore()` skips the API when nothing is stored. A build without `GOOGLE_IOS_CLIENT_ID` says so on the welcome screen; `DEV_SIGN_IN=true` adds the API's development sign-in for working on the app.
- No signed build, TestFlight or App Store: all need a paid Apple Developer account. The docs say which steps that would add.

### Deployment (`docs/deployment/`)

- `release.yml` publishes `ghcr.io/<owner>/world-quiz-api` (one image for every environment) and `world-quiz-site` (per environment), plus the static `shell`/`capitals`/`flags` bundles as an artifact; `ci.yml` builds both images on every PR without pushing. The deploy job (Render for the two Node services, Netlify for the three bundles) runs only with the environment variable `DEPLOY_ENABLED=true`, **which has never been set**: what is live was published by hand with `npm run deploy:web`, so merging a PR changes nothing until someone runs it (`docs/deployment/runbook.md`).
- A deployment configures the app by replacing two files in the shell's bundle: `config.json` and `federation.manifest.json` (`tools/scripts/write-deploy-config.mjs`). The API takes everything from environment variables.
- **Which build is live** is a `<meta name="wq-build">` in each app's `index.html`: a placeholder in the source that `tools/scripts/stamp-build.mjs` replaces in the finished bundle with the commit and the time (`-dirty` when the tree was not clean). Both deploy paths stamp, the three bundles are three deployments that can drift (published one after another, so a deploy that stops halfway leaves a new shell over an old quiz), and `npm run deploy:check` reads all three and says whether they agree.
- There is **no Docker on the development machine**: images are only ever built in CI. `docs/deployment/deploying.md` is the instruction for setting an environment up.

## Gotchas (each cost real debugging time)

- **Never put `PORT`/`HOST`/`NODE_ENV` in a root `.env`**: Nx loads it into every task, the frontend dev servers read `PORT`, and all of them tried to start on the API's port. API variables live in `apps/api/.env` (loaded only for API tasks).
- **Changing `cypress.config.ts` web-server commands needs `npx nx reset`** (or a daemon restart): the inferred `e2e` target is computed from it and cached in the project graph.
- **Never run a production `build` while `nx serve` is running.** The federation dev server serves shared bundles from `dist/`; a build overwrites them and the app turns blank (404 on `*-dev.js`). Restart the dev server after building.
- **Ionic's global CSS is listed in each app's `styles` array** (`project.json`), not `@import`ed from Sass. The federation dev server leaves package `@import`s unresolved (UI falls back to Times), and `@ionic/angular` only exports exact `css/*.css` paths.
- **Ionic caches pages.** `ion-router-outlet` keeps a stack of page instances and reuses an existing one when the same URL is opened again, so a page may be shown again with its old state. Leave a flow with `NavController.navigateRoot(...)` (the quiz does, for exit and "Back to home"), and reset in `ionViewDidLeave` when a page must start fresh next time (`QuizPage` does; `ionViewWillEnter` would also fire when an iOS swipe-back is cancelled).
- **Third-party iframes on a dark page** (Google's sign-in button) get an opaque white backdrop when their colour scheme differs from the page's; give the iframe's container `color-scheme: light` (see `google-sign-in-button.ts`). GIS also cannot change a rendered button: redraw it when the language changes. Google may ignore its `locale` for browsers signed in to Google, and answers 403 to `gsi/client` for some Google sessions (incognito works): not our bug.
- **No solid `ion-button` inside `ion-toolbar`**: Ionic paints its label in the toolbar background colour, which is transparent here.
- **Never write control-character escape sequences in tool input** (a backslash, the letter `u` and four hex digits such as `0000`): they are decoded into raw bytes, and a NUL byte makes git treat the file as binary. `npm run check:control-chars` (also in CI) catches control characters and the U+FFFD replacement character left by such corruption; describe these sequences in words, as here.
- **A backtick inside an inline Angular template closes it.** A component's `template:` is a JavaScript template literal, so one backtick anywhere inside it — in an HTML comment, in a quoted selector, in prose — ends the string, and the build fails far from the cause (`NG5002`, `TS1005`, or a dev server that never comes up and takes the whole E2E run with it). Write comments in a template in plain words, without backticks.
- Nx 23 has no Angular Module Federation support; everything federation-related is `@angular-architects/native-federation` 22.x, set up by hand. TypeScript 6 rejects `baseUrl`; only `paths` is used.
- In Ionic's standalone build, `<ion-input>` has no `componentOnReady`; wait for `customElements.whenDefined('ion-input')` before `setFocus()`.
- **Timestamps sent to the API are whole milliseconds.** `performance.now()` has fractions; the `CLOCK` in `client/quiz-ports` floors them. A fractional `answeredAt` fails the contract (400) and the session is marked `rejected` — unit tests with a manual clock do not catch it.
- **Angular strips whitespace between elements**: `<strong>195</strong> <span>Countries</span>` renders as "195Countries" (also for screen readers). Insert `{{ ' ' }}` where the words must stay apart (welcome stats).
- **API tests talk to a server on 127.0.0.1** (`testing/loopback.ts`, `onLoopback(app)`; `TestApi.app` is that server). Plain `request(expressApp)` listens on `::` and connects to 127.0.0.1; on macOS the port can belong to another program listening on 127.0.0.1 only (WebStorm, DBeaver…) and tests randomly got its 403/404/`{}`. Use `request(api.app)` or `onLoopback()`, never `request(createApp(...))`.
- **CORS must list every HTTP method the API uses** (`http/cors.ts`: `GET, POST, PATCH, DELETE`). Supertest sends no preflight, so a missing method passes the API tests and fails only in the browser (status 0, "server unreachable"); a test checks the preflight.
- **Don't let browsers cache data the player just changed**: `Cache-Control: public, max-age=…` on the leaderboard hid a run the player had just finished. The board is `public, max-age=0, must-revalidate` (revalidated every time, ETag → 304) — not `no-cache`, which Angular's SSR transfer cache refuses to carry (the site would fetch twice).
- **Ionic may show a cached tab page without `ionViewWillEnter`** — e.g. `navigateRoot('/leaderboard')` from a remote's results reuses the tabs and the Leaderboard page. Refresh from data signals (here `SyncService.lastSyncedAt`), not only from lifecycle hooks.
- **An image referenced from a component stylesheet comes out unhashed.** `mask-image: url('…/europe.png')` in a `client/ui` _component_ SCSS is emitted into the bundle as `./media/europe.png`, while the file itself is written as `europe-SBJVXU44.png` — so it 404s in a production build and works perfectly on the dev server, which serves unhashed names. Nothing fails: the element simply loses its mask, and the only way to see it is to look at a production build (`nx run-many -t serve-static` + the page, or the E2E screenshots). The design system's **global** stylesheet (`client/ui/src/styles/*`) rewrites the same `url()` correctly, so that is where an asset-referencing rule belongs — `.wq-option-sketch` lives in `_base.scss` even though only `wq-region-options` uses it.
- **Adding an Angular package fails with `ERESOLVE`** when the lockfile pins another patch: raise all framework packages to the same `~22.1.x`, delete their `node_modules/@angular/<name>` entries from `package-lock.json` and `node_modules`, then `npm install` twice and **confirm with `npm ci`** (the first pass can drop nested deps from the lockfile). Never `--legacy-peer-deps`. See troubleshooting.
- **Angular SSR answers only allowed hosts**: the site's production server returns `400 Header "host" … is not allowed` unless `NG_ALLOWED_HOSTS` lists the host (`site:serve-ssr` sets `localhost`).
- **Design tokens live in `libs/shared/design-tokens`** as mixins; `client/ui/src/styles/_tokens.scss` only applies them. Add a token there, for both themes. One of them is the layout: `--wq-content-max-width` / `--wq-content-gutter` / `--wq-content-width` is the single column `.wq-page` and every floating bar (header, tab bar, action bar, a tour's card) lay out to — a bar with a width of its own does not line up with the cards under it, and `ion-tab-bar` must subtract its own padding and borders because Ionic forces `box-sizing: content-box` on it.
- **The app bootstraps itself twice** (`main.ts` runs again under the federation's import map: `config.json` is fetched twice per load), so two `AuthStore`s exist. Anything that consumes a one-use secret must therefore read it **inside** the Web Lock, not before: the first version of the Keychain store read the refresh token up front, both instances presented the same one, and the API's reuse detection revoked the whole family — the app was signed out on every restart while every unit test passed.
- **Assigning `RESPONSE_INIT.headers` replaces the whole header set**, including `Content-Type`. The site's leaderboard page set only `Cache-Control`, so the server-rendered page arrived without a content type and a browser offered it as a download; `cy.request`-based tests never noticed, only a real browser did (the accessibility spec).
- **The app and the API must share one registrable domain** in a deployment: the refresh token is a `SameSite=Strict` cookie, so `app.example` + `api.example` work but a host's own free subdomains (`*.netlify.app`, `*.onrender.com`) do not — they are on the Public Suffix List, so the browser treats them as separate sites (ADR-010, deploying.md).
- **The iOS federation manifest needs absolute paths** (`/remotes/capitals/remoteEntry.json`). With `remotes/…` Native Federation derives import-map entries that are neither URLs nor rooted paths, the browser logs `es-module-shims: Mapping … does not resolve`, and every quiz fails to load while the manifest and `remoteEntry.json` still return 200. Check it with `npx nx run shell:serve-ios` + the Cypress suite (docs/deployment/ios.md).
- **iOS 26/27 blur the top of an installed web app.** A standalone web app (`display-mode: standalone`) gets the system's status-bar legibility effect painted over its first ~90 px: text drawn there comes out blurred and washed out (the toolbar title's darkest pixel measured 48 against Safari's 27 on an iPhone 17, iOS 27), while the rest of the screen is pixel identical. It is **not** our glass: removing `backdrop-filter`, the toolbar's own layer, its containment or the header's backdrop changed nothing, and plain text on a plain background blurs there too. The effect fades out between 80 px and 95 px, measured with a ladder of probes. `apple-mobile-web-app-status-bar-style: default` avoids it by handing the strip to iOS, but iOS then freezes that strip at the `theme-color` it read **when the app was installed** and never updates it, not even when the page rewrites the meta — a light bar above the dark theme. The fix is the floating header (`wq-page-header`, design-system.md): its glass pill sits low enough that the title measures 27 again. Edges are more sensitive than text — the pill's top edge still smears over 8-11 px where the identical material at the bottom of the screen renders in 1 px — so the header drops the bright top highlight that `glass-chrome` draws, which halves the contrast of what the system can smear. Nothing with a crisp horizontal edge belongs in the top ~100 px. Reproduce it on the iOS 27 simulator: install the app from Safari's Share menu, and reload it after a CSS change with `xcrun simctl terminate <udid> com.apple.webapp` — the dev server's hot reload does not reach an installed web app.
- **The on-screen keyboard is invisible to CSS on iOS, and the page iOS scrolls is the document.** The layout viewport does not shrink when the keyboard opens, so `svh`/`vh`/media queries are unchanged; only `visualViewport` sees it, and it reports _late_ — iOS decides how far to lift the page while the keyboard opens, so a layout that shrinks on the `resize` shrinks too late. Shrinking earlier, on `pointerdown`, is worse: the field moves out from under the finger before the tap completes and no keyboard opens at all. Driving it from the field's `focus` works, but then iOS has lifted the page for the _pre-shrink_ layout and the flag is cut off at the top; the lift is `document.scrollingElement.scrollTop` (not `ion-content`'s scroller, which stays at 0), so the page scrolls itself back once the keyboard has settled. The page must also stop focusing the field by itself on a touch device: iOS opens no keyboard for a programmatic focus, so the player got a focused field with nothing to type on. Testing this on the simulator needs its software keyboard (I/O → Keyboard → Toggle Software Keyboard, Cmd+K): with a hardware keyboard paired, iOS shows only the accessory bar above the fold, which looks exactly like the bug. **The setting follows the app in the foreground**: turning it on in Safari leaves the installed web app without a keyboard, and the same the other way round, so toggle it with the app you are testing on screen. See `quiz-play.ts` and design-system.md.
- **Ionic's Angular build gives a child element no way to know its page is leaving.** It dispatches **no DOM event** for `ionViewWillEnter`/`ionViewWillLeave` (a document-level capture listener for all four saw none during a whole navigation), and for a page pushed over the tabs it never called `ionViewWillLeave` on the page component either — the component's constructor logged, the hook did not. Anything that must react to its page leaving listens to Angular's router instead (`PageChromeState` in `client/ui`, fed by `NavigationStart`). The symptom that led here: the floating header and action bar of the page being left stayed on top of the arriving page for half a second, because Ionic keeps that page alive and does not move it.
- **An `ion-popover` hangs from the element the press landed on.** With an `event`, Ionic measures the anchor from `event.target`, not from the button the handler is on — so a decorative badge inside that button (the bell's unread dot) became the anchor when the press landed on it, and the card opened over the bell. **Everything** drawn inside a button that opens a popover needs `pointer-events: none` — the icon as much as a badge: a press on the bell's 24 px icon opened the list centred on the icon, and one on its 10 px unread dot opened it over the bell. Ionic also places the card on the anchor's own bottom edge, covering its last two pixels, which `--offset-y` answers. Both are invisible to jsdom (the popover is never laid out there) and are covered in Cypress by comparing the two rectangles.
- **A floating header needs `providers: [PageChromeState]` on its page.** Without it `wqFadesWithPage` has nothing to read, and the title pill and back button of the page being left stay lit over the page arriving for the length of the transition. It is a provider, so nothing fails — the bug is only visible in the running app (the countries reference and the release notes both shipped it before it was noticed).
- **Killing `start:quiz` leaves an Nx task lock behind.** The next `api:serve` then prints `Waiting for api:serve:development in another nx process` and never starts, while the frontend dev servers come up as usual — so the app runs and only the API is missing ("server cannot be reached"). Delete `.nx/workspace-data/*.lock` (or run `npx nx reset`) before starting again.
- **A tool that runs `start:quiz` with `PORT` set** (e.g. a preview launcher) makes every dev server take that port, like a root `.env`; unset it (`env -u PORT npm run start:quiz`).

- **Adding a NOT NULL column or FK to a table with data needs a data migration first**: `npx drizzle-kit generate --config apps/api/drizzle.config.ts --custom --name <name>` creates an empty, tracked SQL file (write the `UPDATE`/`DELETE` there), then run `db-generate` for the schema change — see `0001_drop_anonymous_sessions.sql`.
- **A `pg.Pool` must have an `error` listener** (`createPool` in `db/database.ts`): a dropped idle connection otherwise emits an unhandled `error` and kills the API process.
- **drizzle-kit asks a question when one table is dropped and another added in the same diff** ("is `leaderboard_runs` a rename of `challenges`?"), and there is no TTY to answer it in, so generation hangs or picks for you. Generate in two passes: delete the old table from `schema.ts`, run `db-generate` (the drop), then add the new one and run it again.
- **Only commit migrations generated by `db-generate`.** Hand-edited SQL drifts from `drizzle/meta` snapshots and the next generation will be wrong. Change `schema.ts`, generate, review the SQL.
- The zod contract for `SubmitSessionRequest` must stay assignable to the domain's `SessionRecord` (a compile-time check in `sessions.spec.ts`); array schemas that mirror domain `readonly` arrays need `.readonly()`.
